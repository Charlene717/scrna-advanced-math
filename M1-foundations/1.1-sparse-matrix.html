稀疏矩陣：COO / CSR / CSC 編碼的本質

Sparse Matrices: The essence of COO / CSR / CSC encodings

一個典型 10x Genomics 實驗：10,000 細胞 × 20,000 基因 = 2 億個元素。 用 numpy.ndarray 直接放 → 1.6 GB 記憶體。 但其實 90-95% 的元素是 0——記錄那麼多 0 太浪費。

這節從「為什麼稀疏」的具體例子開始，理解 COO、CSR、CSC 三種編碼的數學結構， 親手在互動圖上把矩陣壓進這三種格式，看每種格式記憶體跟運算速度的取捨。 最後解釋為什麼 Scanpy / Seurat 在 PCA / KNN 階段會做格式轉換。
A typical 10x experiment: 10,000 cells × 20,000 genes = 200M entries. Plain numpy.ndarray → 1.6 GB RAM. But 90–95% of entries are 0 — storing those zeros is wasteful.

We start from the "why sparse" concrete example, work through COO, CSR, CSC encodings, interactively compress a matrix into each format, and compare memory vs runtime trade-offs. Finally, why Scanpy / Seurat switch formats between PCA and KNN.

§0 故事：1.6 GB 還是 100 MB？Story: 1.6 GB or 100 MB?

你剛拿到 10x 跑出來的細胞-基因矩陣，10,000 個細胞、20,000 個基因。你打開 Jupyter：

You just received a 10x cell × gene matrix: 10,000 cells, 20,000 genes. Open Jupyter: 

# Memory bomb
import numpy as np
X = np.zeros((10000, 20000), dtype=np.float64)
# X 已經吃掉 1.6 GB
print(X.nbytes / 1e9)  # 1.6

但你打開細胞數，每個細胞平均只有 1500 個基因有 count——其他 18500 都是 0。

But each cell averages only 1500 detected genes — the other 18500 are 0.

§1 三種稀疏編碼：COO · CSR · CSCThree encodings: COO · CSR · CSC

三種編碼解決同一個問題（只記錄非零），但排序與索引方式不同，造成不同操作的速度差。

Three encodings solve the same problem (store only non-zeros), but differ in ordering and indexing, leading to different operation costs.

1.1 COO (Coordinate format)

最直觀：三個平行陣列 (row, col, val)，每筆 = 一個非零元素。

Most intuitive: three parallel arrays (row, col, val), one entry per non-zero.

$$\text{COO}(A) = \{(i_k, j_k, v_k) : v_k \neq 0\}_{k=1}^{\text{nnz}}$$
nnz = number of non-zeros。3 個長度 nnz 的陣列
nnz = non-zero count. Three nnz-length arrays

記憶體: $\text{nnz} \times (4 + 4 + 8) = 16$ bytes per nnz (int32 row + int32 col + float64 val)

Memory: $\text{nnz} \times 16$ bytes (int32 row + int32 col + float64 val)

看 §0 那個 5×8 矩陣的 COO 編碼

COO encoding of the §0 5×8 matrix

row = [0, 0, 1, 2, 2, 3, 4, 4]
col = [1, 4, 5, 0, 3, 6, 2, 7]
val = [3.0, 2.0, 1.0, 4.0, 5.0, 2.0, 1.0, 3.0]

1.2 CSR (Compressed Sparse Row)

把 COO 的「row」陣列壓縮成「每列從第幾個非零開始」的指標：

Compresses COO's row array into "where each row starts" pointers:

$$\text{CSR}(A) = \begin{cases} \text{values}[k] = v_k \\ \text{col\_idx}[k] = j_k \\ \text{row\_ptr}[i] = \text{累計到第 } i \text{ 列為止的非零數} \end{cases}$$

第 $i$ 列的非零元素位置 = values[row_ptr[i] : row_ptr[i+1]]。

Row $i$'s non-zeros = values[row_ptr[i] : row_ptr[i+1]].

記憶體: $\text{nnz} \times 12 + (n+1) \times 4$ bytes。列向操作（row-slicing、SpMV）特快。

Memory: $\text{nnz} \times 12 + (n+1) \times 4$ bytes. Row-slicing and SpMV are very fast.

1.3 CSC (Compressed Sparse Column)

跟 CSR 對稱——壓縮的是「col」陣列，欄向操作特快。

Mirror of CSR — compresses "col" array, column operations fast.

§3 CSR 的 row_ptr 是怎麼算的？How is CSR's row_ptr computed?

這節我們把 §0 那個 5×8 矩陣手動編成 CSR。理解 row_ptr 的構造邏輯。

Manually encode the §0 5×8 matrix into CSR. Understand row_ptr construction.

3.1 五步驟構造

3.1 Five-step construction

  1. 逐列掃描矩陣，記下每列的非零元素Scan rows; record each row's non-zeros
  2. 第 0 列有 2 個非零 (在 col 1, 4)，值 3, 2 → values 加 [3, 2], col_idx 加 [1, 4] Row 0 has 2 non-zeros (cols 1, 4, vals 3, 2) → values += [3, 2], col_idx += [1, 4]
  3. 第 1 列有 1 個 (col 5, val 1) → values 加 [1], col_idx 加 [5] Row 1 has 1 (col 5, val 1) → append
  4. ...持續到第 4 列...continue through row 4
  5. row_ptr 是「每列累計」：row_ptr[0]=0, row_ptr[1]=row_ptr[0]+(第 0 列 nnz)=2，以此類推 row_ptr is cumulative: row_ptr[0]=0, row_ptr[1]=row_ptr[0]+(row-0 nnz)=2, etc.

手算結果

Hand-computed result

values = [3.0, 2.0, 1.0, 4.0, 5.0, 2.0, 1.0, 3.0]
col_idx = [1, 4, 5, 0, 3, 6, 2, 7]
row_ptr = [0, 2, 3, 5, 6, 8]

row_ptr 的長度 = 列數 + 1。最後一個值 = nnz = 8。

row_ptr length = num_rows + 1. Last value = nnz = 8.

驗證讀取：拿第 2 列

Verify: read row 2

row_ptr[2] = 3, row_ptr[3] = 5。所以第 2 列的非零在 values[3:5] = [4.0, 5.0]，欄位 col_idx[3:5] = [0, 3]。✓

row_ptr[2] = 3, row_ptr[3] = 5. Row 2 non-zeros = values[3:5] = [4.0, 5.0], cols = col_idx[3:5] = [0, 3]. ✓

§5 SpMV：稀疏矩陣乘向量的複雜度SpMV complexity

SpMV (Sparse Matrix-Vector multiply) $\mathbf{y} = A\mathbf{x}$ 是 PCA、KNN graph、Leiden 等核心運算。 Dense 是 $O(np)$，稀疏可以做到 $O(\text{nnz})$。

SpMV $\mathbf{y} = A\mathbf{x}$ is the core operation in PCA, KNN graph, Leiden, etc. Dense: $O(np)$. Sparse: $O(\text{nnz})$.

5.1 CSR 的 SpMV 演算法

5.1 SpMV with CSR

# y = A * x
y = np.zeros(n)
for i in range(n):
    for k in range(row_ptr[i], row_ptr[i+1]):
        y[i] += values[k] * x[col_idx[k]]

內外迴圈總次數 = nnz。對 95% 稀疏的 scRNA 矩陣，比 dense 快 20 倍。

Total iterations = nnz. For 95%-sparse scRNA, this is 20× faster than dense.

5.2 為什麼 CSR 快、CSC 在 SpMV 比較慢？

5.2 Why CSR fast, CSC slower for SpMV?

SpMV 算 $y = Ax$ 是「對每列 $A_i$ 跟 $x$ 做內積」——天然按列走，所以 CSR 把每列收成連續記憶體最有效率。CSC 要算 $y$ 必須「對每欄做累加」，cache locality 較差。

SpMV computes "row $A_i$ · x" — naturally row-wise. CSR's contiguous-per-row layout maximizes cache locality. CSC requires "accumulate column-wise into y" — worse cache behavior.

§6 為什麼 PCA 用 CSC、KNN 用 CSRWhy PCA uses CSC, KNN uses CSR

看到底層後，這兩個選擇就很自然：

Once you see the internals, both choices are natural:

PCA 的核心運算PCA's core: 是「對每個 feature (gene) 算 mean 跟 variance」——欄向走訪。 CSC 把每欄存連續，scan 一遍就拿到該 gene 的所有值。CSR 要對每列查 col_idx 找 gene，慢得多。 "compute mean/variance per feature (gene)" — column-wise traversal. CSC stores columns contiguously. CSR would require scanning every row for each gene — much slower.
KNN 的核心運算KNN's core: 是「對每個 cell 跟其他 cell 比距離」——列向走訪。 CSR 把每列存連續，拿到 cell 表現量直接做 dot product。 "compute distance from each cell to others" — row-wise traversal. CSR stores rows contiguously; get cell vector, dot product directly.
在 scanpy 裡的轉換Conversion in Scanpy: scanpy 在 sc.tl.pca 前會把 CSR 轉 CSC（隱式）；之後 sc.pp.neighbors 又會用 CSR 表示 graph。轉換成本是 $O(\text{nnz})$——對大資料不該頻繁來回切換。 Scanpy implicitly converts CSR → CSC before sc.tl.pca; then back to CSR for the graph in sc.pp.neighbors. Conversion cost $O(\text{nnz})$ — don't switch repeatedly.

§7 AnnData 整合 + 限制AnnData integration + limits

7.1 AnnData 的儲存設計

7.1 AnnData storage design

AnnData (Scanpy 的核心物件) 預設用 CSR 儲存 .X。原因：

AnnData (Scanpy's core) defaults to CSR for .X. Reasons:

  • 大多數操作（QC 算每細胞的 total_counts、normalize 除以 size factor）都是 per-cell，即列向
  • Most operations (QC compute per-cell total_counts, normalize divide by size factor) are per-cell = row-wise
  • cell-by-cell 的子集 (adata[:, mask]) 在 CSR 上 O(nnz_subset)
  • cell-by-cell subset (adata[:, mask]) in CSR is O(nnz_subset)
  • PCA 階段才轉 CSC（隱式 + 一次性）
  • CSC conversion only at PCA stage (implicit, one-shot)
import scanpy as sc
adata = sc.read_10x_h5("filtered.h5")
# adata.X is csr_matrix by default
print(type(adata.X))  # <class 'scipy.sparse.csr_matrix'>

# operations that stay sparse:
sc.pp.calculate_qc_metrics(adata, inplace=True)  # row-wise OK
sc.pp.normalize_total(adata)                       # row-wise OK
sc.pp.log1p(adata)                                 # row-wise OK

# operations that DENSIFY (memory risk):
sc.pp.scale(adata)        # z-score: subtraction → 0 entries become non-zero → matrix densifies
sc.pp.regress_out(adata, ["total_counts"])  # also densifies

7.2 哪些 scanpy 操作會「densify」?

7.2 Which Scanpy ops "densify"?

記憶體陷阱Memory trap: sc.pp.scale 與 sc.pp.regress_out 會減 mean—— 讓原本是 0 的元素變成非零，矩陣從稀疏變 dense。對 10k × 2000 HVG，dense 才 160 MB 還好； 但對 1M × 2000 cells 就會炸（16 GB）。實務上會先 HVG 篩選把矩陣縮小再做 scale。 sc.pp.scale and sc.pp.regress_out subtract means — zero entries become non-zero, matrix densifies. For 10k × 2000 HVG, dense is 160 MB — fine; but 1M × 2000 cells gives 16 GB. Practice: HVG-filter first to shrink before scale.
